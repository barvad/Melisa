# Технико-экономическое обоснование выбора архитектуры RAG-системы

---

## 1. Анализ задачи и контекст

### 1.1 Исходные данные
- **Тип системы:** RAG-бот для работы с корпоративной базой знаний
- **Объем данных:** 60 000 документов
- **Модель эмбеддингов:** Xenova/distiluse-base-multilingual-cased-v2 (размерность вектора 512)
- **Модель генерации:** Groq (openai/gpt-oss-120b)
- **Векторное хранилище:** PostgreSQL + pgvector
- **Структура хранения:** Тексты чанков и ссылки хранятся в той же таблице, что и вектор
- **Ключевое ограничение:** Конфиденциальность данных

### 1.2 Критические требования
- Обеспечение безопасности корпоративных данных
- Интеграция с существующей PostgreSQL-инфраструктурой
- Работа с многоязычным контентом
- Масштабируемость при росте объема данных

## 3. Инфраструктурные требования

## 4. Варианты архитектуры

### Вариант 1: Локальные эмбеддинги + Облачная LLM (Рекомендуемый)


Компоненты:
- LLM: Groq (openai/gpt-oss-120b) через API
- Эмбеддинги: Xenova/distiluse-base-multilingual-cased-v2 (локально)
- Векторная БД: pgvector
- Хранение: Единая таблица (вектор + текст чанка + ссылка)



Инфраструктура:
- Сервер БД: 8 vCPU, 32 GB RAM, 200 GB SSD
- Стоимость: $300-500/мес + оплата Groq API

Плюсы:
✓ Полный контроль над данными документов
✓ Высокое качество генерации через Groq
✓ Простая интеграция с существующей PostgreSQL
✓ Единое хранилище гарантирует консистентность
✓ Индекс HNSW обеспечивает быстрый поиск по 60K векторов

Минусы:
✗ Данные запросов уходят в Groq
✗ Зависимость от внешнего API


### Вариант 2: Полностью локальное решение

Компоненты:
- LLM: Локальная модель (Llama 3 8B / Mistral)
- Эмбеддинги: Xenova/distiluse-base-multilingual-cased-v2
- Векторная БД: pgvector

Инфраструктура:
- Сервер: 16 vCPU, 64 GB RAM, GPU (опционально), 500 GB SSD
- Стоимость: $800-1500/мес

Плюсы:
✓ Полная конфиденциальность
✓ Нет зависимости от внешних сервисов

Минусы:
✗ Качество генерации ниже Groq (120B vs 8B)
✗ Высокая стоимость инфраструктуры

Плюсы:
✓ Минимальные требования к серверу

Минусы:

✗ Критично для конфиденциальности
✗ Высокая стоимость при индексации 60K документов


### Вариант 4: Высоконагруженное решение


Компоненты:

## 5. Итоговые рекомендации

### 5.1 Выбор: Вариант 1 (Локальные эмбеддинги + Groq LLM + pgvector)

**Обоснование выбора:**

1. **Соответствие требованиям безопасности**
   - Тексты документов и ссылки хранятся локально в PostgreSQL
   - Эмбеддинги рассчитываются локально, данные не покидают периметр
   - Groq получает только контекст запроса (не базу знаний целиком)

2. **Оптимизация под объем данных (60K документов)**
   - Индекс HNSW в pgvector обеспечивает O(log n) поиск
   - Размер индекса для 60K векторов размерности 512: не более 300 MB
   - Индекс полностью помещается в RAM, гарантируя высокую скорость
   - QPS > 1000 при полном попадании в кэш

3. **Архитектурные преимущества pgvector**
   - Хранение текста чанка и ссылки в той же таблице, что и вектор
   - Атомарность операций: при вставке документа гарантированно сохраняются и текст, и вектор
   - Возможность сложной фильтрации через SQL без дополнительных сервисов

4. **Эффективность выбранной модели эмбеддингов**
   - Xenova/distiluse-base-multilingual-cased-v2 оптимизирована для CPU
   - Размерность 512 хорошо сбалансирована для pgvector
   - Поддержка русского языка в многоязычном контексте

5. **Качество генерации**
   - Groq с моделью 120B параметров обеспечивает генерацию уровня SOTA
   - Отсутствие необходимости в GPU на локальной стороне

### 5.2 Ожидаемые метрики производительности

| Метрика | Значение |
|---------|----------|
| **Размер индекса pgvector (60K векторов, dim=512)** | не более 300 MB |
| **Время индексации (HNSW)** | ~5-10 минут |
| **Скорость поиска (latency p95)** | 30-50 ms |
| **Пропускная способность (QPS)** | 1000-2000 |
| **Точность поиска (recall@10)** | 0.90-0.95 |
| **Время генерации эмбеддингов (пакетно, 60K документов)** | 2-3 часа (CPU) |
| **Полное время ответа RAG** | 2-5 секунд |


### 5.3 Заключение

Предлагаемая архитектура на базе **pgvector** в сочетании с локальными эмбеддингами Xenova/distiluse-base-multilingual-cased-v2 и облачной LLM Groq обеспечивает:

- **Безопасность корпуса документов** — тексты и ссылки хранятся локально, не покидают периметр
- **Оптимальную производительность для 60K документов** — индекс HNSW полностью помещается в RAM
- **Высокое качество генерации** — модель 120B параметров через Groq API
- **Простоту реализации** — единая таблица в PostgreSQL гарантирует консистентность данных
- **Экономическую эффективность** — отсутствие затрат на GPU, оплата только за генерацию

Данное решение оптимально для корпоративного RAG-бота с объемом базы знаний 60 000 документов при требованиях к конфиденциальности данных и высокому качеству ответов.
